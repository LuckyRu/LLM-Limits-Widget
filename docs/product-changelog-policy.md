# Правило продуктового changelog

Каждый GitHub Release должен содержать продуктовые release notes. Notes строятся автоматически из Conventional Commits между предыдущим тегом `v*` и текущим релизным тегом.

## Категории

- `feat:` — «Новые возможности»;
- `fix:`, `perf:`, `revert:` — «Исправления и улучшения»;
- `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:` и неизвестные типы — «Технические изменения».

Сообщение после типа коммита должно быть коротким и понятным пользователю. Scope допускается: `feat(claude): ...`. Breaking change отмечается `!` и получает префикс `BREAKING`.

## Pipeline

`.github/workflows/release.yml` запускает `scripts/generate-product-changelog.ps1` перед публикацией GitHub Release. Скрипт:

1. находит предыдущий тег `v*`;
2. собирает сообщения коммитов в диапазоне `previous-tag..current-tag`;
3. раскладывает их по продуктовым категориям;
4. добавляет описание четырёх артефактов релиза;
5. передаёт готовый Markdown в `gh release create --notes-file`.

Если пользовательские изменения отсутствуют, раздел сохраняется с явным сообщением об этом. Поэтому каждый релиз имеет предсказуемую структуру и не зависит от GitHub auto-generated notes.
