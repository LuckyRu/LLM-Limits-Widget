# ADR 0008: Гибридный транспорт лимитов Claude Pro

Дата: 2026-08-12  
Статус: accepted

## Контекст

Claude Code предоставляет два полезных локальных канала:

1. интерактивный statusLine с JSON-полями rate limits;
2. прямой запуск авторизованного CLI с командой /usage и output-format json.

StatusLine быстрее и не требует отдельного процесса, но работает только при активной Claude Code-сессии и обновляется событийно. Прямой /usage можно вызвать автономно, но запуск процесса и сетевой запрос дороже по времени и ресурсам.

## Решение

Использовать гибридный provider:

1. statusLine bridge принимает быстрые обновления, когда активна Claude Code CLI-сессия;
2. provider хранит последний snapshot и его время получения;
3. если snapshot свежее TTL, виджет показывает его;
4. если snapshot устарел, provider запускает авторизованный Claude Code CLI с /usage;
5. прямой /usage также запускается при старте виджета и по ручной команде обновления;
6. при расхождении источников более свежий прямой /usage считается authoritative snapshot;
7. если оба источника недоступны, показывается stale или unavailable, но не нулевой остаток.

## Базовые интервалы

- запуск виджета: один direct refresh;
- активная Claude Code CLI-сессия: fallback polling /usage каждые 3–5 минут после истечения TTL;
- неактивная сессия: polling каждые 15–30 минут;
- ручное обновление: немедленный direct refresh;
- запрет параллельных запросов и обязательный timeout/backoff.

Значения интервалов являются стартовыми и могут быть скорректированы по измерениям latency, стабильности и нагрузке.

## Почему

- statusLine даёт быстрый push-like путь;
- /usage работает без активной CLI-сессии;
- smoke test показал num_turns: 0, duration_api_ms: 0 и total_cost_usd: 0;
- не нужны cookies, OAuth token или Anthropic API key;
- stale data явно контролируется через TTL;
- архитектура переносит отсутствие statusline в Claude Desktop.

## Что важно не перепутать

Наличие окна Claude Desktop не гарантирует, что Claude Code statusLine будет вызван. StatusLine — канал Claude Code CLI. Desktop usage ring остаётся ручным UI-источником для сверки.

## Последствия

- provider становится сложнее, чем один источник;
- нужно парсить текстовое поле result у /usage;
- потребуется диагностировать источник каждого snapshot;
- direct polling не должен быть слишком частым;
- при конфликте значений UI должен показывать время и источник последнего обновления.
