# Надёжный конвейер получения лимитов Claude и Codex

**Статус:** implemented (первый production-срез)  
**Дата:** 2026-08-15  
**Область:** локальный виджет для персональных планов. Никаких API-ключей, cookie браузера или облачного бэкенда.

## Решение в одном абзаце

Виджет не должен зависеть от единого poller-а. Для каждого провайдера работает свой `ProviderSupervisor`: он принимает события от быстрых источников, планирует редкие контрольные чтения, не допускает параллельных запусков, сохраняет последний корректный снимок на диск и управляет повторами каждого транспорта отдельно. При любой временной проблеме пользователь видит последние достоверные данные со статусом свежести, а система восстанавливается сама. Внимание пользователя требуется только при устойчивой проблеме авторизации или при несовместимом обновлении CLI.

## Реализовано

- `ProviderSupervisor` с single-flight, per-provider backoff, circuit breaker semantics и отдельным расписанием: Codex — 2 минуты, Claude — 5 минут без свежего status line.
- Атомарный last-known-good cache в `%LOCALAPPDATA%\LLMLimitsWidget\state`; старт без сети восстанавливает данные как stale, а не как нули.
- Claude status line bridge публикует named event, а виджет дополнительно наблюдает snapshot через `FileSystemWatcher`; прямой `claude -p /usage` остаётся автономным fallback.
- Codex использует одну долгоживущую `app-server` сессию, сериализует запросы и пересоздаёт её после сбоя, 30 минут или 60 чтений.
- Resume Windows запускает один jittered refresh после короткой паузы.

Включение/изменение `statusLine` в конфигурации Claude Code намеренно не происходит молча: личный конфиг пользователя остаётся его собственностью. Если status line не настроен, прямой CLI fallback продолжает обновлять лимиты автоматически.

## Что меняем относительно текущего прототипа

Текущие риски:

- один глобальный таймер раз в 30 секунд обслуживает оба провайдера;
- каждый запрос Codex поднимает новый `codex app-server`;
- ручное и фоновое обновления могут пересечься;
- последний успешный результат живёт только в памяти;
- ошибки не имеют типов, нет backoff, circuit breaker и проверки совместимости протокола;
- Claude status line читается только следующим тиковым опросом, а не как событие.

Целевое правило: обновление интерфейса может происходить каждую минуту для обратного отсчёта, но это **не** означает сетевой или процессный запрос каждую минуту.

## Архитектура

```text
Claude statusLine ──► bridge ──► atomic snapshot + local signal ─┐
Claude CLI /usage ───────────────────────────────────────────────┤
                                                               ProviderSupervisor ─► reducer ─► UI
Codex app-server session ────────────────────────────────────────┤        │
                                                               state store ◄──────┘
                                                                   │
                                                        last-known-good cache
```

### Общие компоненты

| Компонент | Ответственность |
| --- | --- |
| `ProviderSupervisor` | Один актор на провайдера: расписание, single-flight, retry, circuit breaker, восстановление после сна/перезапуска. |
| `ILimitTransport` | Изолированный транспорт: получить, проверить и нормализовать данные без изменения UI. |
| `LimitsReducer` | Принимает только валидные снимки, выбирает более свежий источник, не даёт старому событию затереть новое. |
| `ProviderStateStore` | Атомарно хранит последний корректный снимок и состояние здоровья в `%LOCALAPPDATA%\LLMLimitsWidget\state`. |
| `TransportHealth` | Классифицирует ошибки и хранит число сбоев, backoff, состояние breaker-а и время последнего успеха. |
| `Diagnostics` | Пишет безопасные структурированные события; показывает короткое состояние в tray, не спамит окнами. |

### Контракт данных

Каждый транспорт возвращает не просто проценты, а `AcquisitionResult`:

```text
provider, source, receivedAtUtc, observedAtUtc?, protocolVersion?,
windows[], validity, freshnessHint, failureKind?, diagnosticCode?
```

`receivedAtUtc` — время, когда виджет получил результат; именно оно определяет, можно ли заменить текущий снимок. `observedAtUtc` — время самого события, если его передал провайдер. В состояние и логи не попадают raw stdout, токены, cookie или команды с секретами.

### Состояния для UI

| Состояние | Поведение |
| --- | --- |
| `ColdStart` | Числа не рисуются как реальные: нейтральная загрузка до первого валидного снимка. |
| `Fresh` | Последний корректный снимок укладывается в ожидаемый интервал свежести. |
| `Aging` | Данные ещё пригодны, но фоновая проверка уже назначена. |
| `Stale` | Показываются последние значения с неброским индикатором давности. |
| `Recovering` | Идёт разрешённая попытка после backoff/circuit breaker. |
| `ActionRequired` | Авторизация или совместимость требует действия; данные не выдумываются и не заменяются нулями. |

## Общая политика надёжности

### Single-flight и приоритеты

У каждого `ProviderSupervisor` один исполнитель. Таймер, файловое событие, resume Windows и команда «Обновить» не создают несколько процессов: они ставят одну объединённую работу в очередь. Ручное обновление повышает приоритет ближайшей работы, но не прерывает уже корректно выполняющийся запрос.

### Повторы и circuit breaker

Ошибки разделяются на:

- **transient** — timeout, процесс неожиданно завершился, временная сеть, lock файла;
- **authentication** — сессия CLI истекла или пользователь вышел;
- **incompatible** — изменился протокол/формат ответа либо пропал нужный capability;
- **invalid-data** — JSON/текст прочитан, но проценты или reset timestamp семантически неверны.

Для transient-ошибок: full-jitter backoff `5 с → 15 с → 45 с → 2 мин → 5 мин → 15 мин → максимум 30 мин`. После трёх последовательных ошибок конкретный транспорт открывает circuit breaker: не запускается до cooldown, затем разрешается одна half-open попытка. Успех сразу закрывает breaker. Другой транспорт этого же провайдера продолжает работать.

Для authentication и incompatible не нужен горячий retry-loop: транспорт помечается `ActionRequired` и проверяется редко (через 30–60 минут, а также по ручной команде, перезапуску приложения или изменению версии CLI). Один tray-индикатор появляется только после устойчивой проблемы; повторные уведомления подавляются.

### Долговечный last-known-good cache

После каждого валидного результата пишется один атомарный JSON-файл: временный файл в той же папке, flush, затем replace/move. В нём: нормализованные лимиты, источник, время получения, версия схемы и health metadata. На старте виджет сразу восстанавливает этот снимок как `Aging`/`Stale`, а затем запускает контролируемую проверку. Неудача никогда не заменяет корректные значения нулями или правдоподобными заглушками.

Файл с частичной записью, неверной схемой или невозможными значениями игнорируется. Валидируются диапазоны процентов, конечность чисел, существование reset timestamp и разумный временной диапазон. Старый результат не может перезаписать более новый.

### Самовосстановление

- При выходе Windows из сна все ожидаемые интервалы пересчитываются, добавляется небольшая случайная задержка и выполняется один refresh, а не лавина процессов.
- Каждый дочерний процесс имеет timeout; при зависании завершается всё дерево процесса.
- Watchdog замечает неответившую задачу супервизора, перезапускает транспорт и сохраняет диагностический код.
- Изменение версии/пути CLI сбрасывает только breaker соответствующего транспорта и запускает capability probe.
- Локальные события (из status line) доставляются через named event, а `FileSystemWatcher` служит резервом; оба механизма дедуплицируются по sequence/time.
- Все интервалы получают jitter, поэтому повторный запуск после логина или resume не создаёт одновременные всплески.

## Claude

### Каналы и приоритет

1. **Быстрый канал — Claude Code status line.** Наш bridge принимает JSON `rate_limits`, валидирует его, атомарно обновляет snapshot и посылает локальный сигнал. Официальный status line поддерживает `rate_limits.five_hour` и `rate_limits.seven_day`, умеет event-driven вызовы и `refreshInterval`; поля могут быть `null` до первого ответа. [Документация Claude Code](https://code.claude.com/docs/en/statusline)
2. **Контрольный канал — `claude -p /usage`.** Он получает данные через уже авторизованный Claude Code CLI и используется на старте, при устаревшем status line, по ручной команде и для периодической сверки.
3. **LKG cache.** Если оба канала временно недоступны, показывает только сохранённый валидный снимок с давностью.

### Расписание Claude

| Условие | Действие |
| --- | --- |
| Принят status line event | Немедленно применить снимок; прямой CLI не запускать. |
| Status line свежий (< 3 мин) | Прямой CLI сверяется раз в 15 минут. |
| Status line отсутствует/устарел | `claude -p /usage` раз в 5 минут. |
| Cold start, resume, ручной refresh | Одна прямая попытка сразу через single-flight. |
| Transient failure CLI | Backoff выше, не стирая LKG. |

Bridge должен быть короткоживущим (меньше примерно 300 мс) и не выполнять сетевую работу: статусная строка Claude Code может отменять старый запуск при следующем событии. Настройку `statusLine` нельзя молча перезаписывать. Нужен проверяющий компонент, который обнаружит отсутствие/замену конфигурации, а включение fast channel будет явным одноразовым действием пользователя. Даже без него продукт полностью работает через прямой канал.

Парсер вывода `/usage` считается изменчивым контрактом. Он должен иметь набор versioned fixtures, несколько строго ограниченных форматов, диагностику `ClaudeUsageFormatChanged` и fallback на LKG, а не подставлять прочерки как данные.

## Codex

### Канал

Основной канал — локальный `codex app-server` и запрос лимитов. На практике он работает с текущей авторизацией ChatGPT, но публично документированный стабильный контракт именно для метода чтения лимитов отсутствует. Поэтому это **capability-based experimental transport**, а не API, на которое можно безусловно опереться.

### Долгоживущая сессия вместо процесса на каждый тик

`CodexAppServerSession` — актор, который владеет одним дочерним `codex app-server --stdio`:

- выполняет initialize и capability probe при старте;
- сериализует request id и чтение stdout;
- делает чтение лимитов раз в 2 минуты в здоровом состоянии;
- принимает ручной refresh в ту же очередь;
- перезапускает сессию после timeout, закрытия pipe, protocol error или смены версии;
- профилактически пересоздаёт сессию после ограниченного числа запросов или 30 минут жизни.

При трёх transient-сбоях сессия открывает breaker и пробует восстановление по общей политике. При повторяющемся отсутствии метода или несовместимой схеме частые запуски прекращаются: остаётся LKG, транспорт ждёт изменения версии/ручной проверки/редкого probe. Это не должно превращаться в бесконечный запуск консоли или забирать лимит задач.

`Codex` не должен падать на один известный JSON shape: capability probe и parser contract tests фиксируют допустимые поля. Любое неизвестное ведёт к `CodexProtocolChanged`, логам с redacted metadata и сохранению старого результата.

## Правила выбора снимка

1. Снимок применяется только после синтаксической и семантической проверки.
2. Более поздний `receivedAtUtc` выигрывает; старый status line event не может затереть новый прямой результат.
3. При почти одновременных валидных снимках прямой CLI может иметь больший приоритет для Claude, а подтверждённый app-server — для Codex.
4. Неудачный результат влияет только на health транспорта, но не на лимиты в UI.
5. Обратный отсчёт пересчитывается локально из сохранённого reset timestamp; для него не нужен новый запрос к провайдеру.

## Диагностика без лишней тревоги

В JSONL-логи пишутся: provider, transport, result class, duration bucket, cache age, number of failures, breaker transition, CLI version и redacted diagnostic code. Raw response и секреты запрещены. В tray доступны «Обновить», «Состояние источников» и «Открыть логи».

Уведление допустимо только когда: нет ни одного корректного снимка либо `ActionRequired` сохраняется после нескольких контролируемых попыток. Обычные временные ошибки, backoff и восстановление остаются бесшумными.

## Приёмочные сценарии

- Перезапустить виджет без сети: немедленно показать LKG как stale, без нулей и выдуманных чисел.
- Одновременно нажать «Обновить», дождаться таймера и file event: для каждого провайдера активен только один дочерний процесс/запрос.
- Завершить CLI/app-server во время чтения: процесс-tree очищен, следующий half-open запуск восстанавливает источник.
- Подать обрезанный snapshot, `null`, невалидный процент или невозможную дату: UI и LKG не портятся.
- Не получать status line 12 часов: Claude продолжает обновляться прямым CLI каждые 5 минут.
- Потерять авторизацию: после ограниченных попыток показать одно понятное действие, без повторного открытия консоли и без спама.
- Обновить Claude/Codex CLI: сбросить breaker, повторно выполнить capability probe и применить данные только после contract validation.
- Уйти в сон и вернуться: один jittered refresh, без параллельных процессов.
- Проверить логи и state-файлы: нет токенов, cookie, raw stdout и персональных ответов провайдеров.

## Порядок реализации

1. Ввести общий domain: `AcquisitionResult`, `TransportHealth`, atomic `ProviderStateStore`, per-provider supervisor и single-flight. Существующие транспорты оставить адаптерами.
2. Перевести Claude на event-driven bridge + watcher/named event, verifier конфигурации и надёжный прямой fallback с fixture-тестами.
3. Заменить запуск Codex app-server раз в 30 секунд на актор долгоживущей сессии, capability probe и version-aware restart.
4. Добавить tray diagnostics, chaos/integration тесты и сценарии resume/auth/protocol-change.

Каждый этап должен сохранять текущий рабочий fallback: новый механизм вводится рядом со старым, проверяется на реальном CLI, затем становится primary.
