# Реализация FloatingOverlay

Дата: 2026-08-13  
Статус: реализовано в текущем spike

Документ описывает техническую реализацию компактного WPF-виджета лимитов и, в первую очередь, систему безопасного размещения окна. Исходный код находится в [spikes/FloatingOverlay](../../spikes/FloatingOverlay), тесты геометрии — в [spikes/FloatingOverlay.GeometryTests](../../spikes/FloatingOverlay.GeometryTests).

## 1. Границы компонентов

```text
App
 ├─ MainWindow                         WPF-визуал и пользовательские события
 │   ├─ WidgetAppearance                layout, масштаб, прозрачность, радиус
 │   ├─ Theme.xaml                      дизайн-токены и стили
 │   └─ WindowPlacementController       нативная геометрия и защита позиции
 └─ NotifyIcon + ContextMenuStrip       tray-команды

WidgetSettingsStore                     JSON-профиль пользователя
WindowPlacementGeometry                  чистая геометрия без Win32-зависимостей
```

`MainWindow` не вычисляет координаты окна самостоятельно. Он сообщает контроллеру о необходимости восстановить, нормализовать, изменить размер или сохранить позицию. Это предотвращает расхождение между WPF-состоянием и реальным HWND.

Основная реализация:

- [MainWindow.xaml.cs](../../spikes/FloatingOverlay/MainWindow.xaml.cs) — жизненный цикл окна, layout, меню и resize-жесты;
- [WindowPlacementController.cs](../../spikes/FloatingOverlay/WindowPlacementController.cs) — Win32 placement controller;
- [WidgetSettings.cs](../../spikes/FloatingOverlay/WidgetSettings.cs) — схема и безопасное хранение настроек;
- [app.manifest](../../spikes/FloatingOverlay/app.manifest) — `PerMonitorV2` DPI awareness.

## 2. Две системы координат

Визуальная часть WPF работает в device-independent pixels (DIP). Win32 возвращает положение HWND, мониторов и taskbar в физических пикселях. Контроллер размещения использует только физические пиксели и типы `NativeRect` / `PixelRect`.

Это правило обязательно:

1. WPF меняет `Width` и `Height` в DIP.
2. Контроллер получает фактический `GetWindowRect` в физических пикселях.
3. Все clamp, snap, anchor и относительные координаты вычисляются в одной физической системе.
4. Вызов `SetWindowPos` получает уже физические координаты.

Manifest включает `PerMonitorV2`, поэтому при переходе между мониторами с разным scaling окно получает корректное DPI-событие. Нельзя смешивать `ActualWidth` / `ActualHeight` с Win32-координатами без явного пересчёта.

## 3. Политика допустимой области

Безопасная область — физический прямоугольник монитора Win32 `rcMonitor`:

```text
monitorBounds = [Monitor.Left, Monitor.Top,
                 Monitor.Right, Monitor.Bottom]
```

`rcWork` намеренно не используется для ограничения позиции. Поэтому виджет может находиться поверх Windows taskbar — это основной целевой сценарий размещения. Защита ограничивает только внешний физический периметр дисплея.

Следствия:

- нижний anchor действительно означает низ экрана, включая область taskbar;
- taskbar сверху, слева или справа не создаёт искусственный зазор;
- отрицательные координаты монитора поддерживаются;
- если окно шире или выше монитора, его начало фиксируется у соответствующего верхнего/левого края, чтобы drag-поверхность оставалась доступной.

При локальной проверке на мониторе `3440 x 1440` с `rcWork.Bottom = 1392` окно было размещено с `Bottom = 1440`. Оно перекрывало taskbar, но не выходило за физический низ дисплея.

## 4. Геометрические операции

`WindowPlacementGeometry` — чистый слой, который не вызывает Win32 API.

### Restore

`Restore` получает bounds монитора, текущий размер окна, относительные координаты и anchors. Сначала вычисляется позиция:

- `Left` — левый край монитора;
- `Right` — `monitor.Right - window.Width`;
- без горизонтального anchor — интерполяция по `RelativeX`;
- аналогично для вертикальной оси.

Затем результат проходит через `ClampAndSnap` с нулевым snap distance. Поэтому повреждённый или устаревший профиль не может вернуть окно за пределы монитора.

### ClampAndSnap

Операция выполняется отдельно по X и Y:

1. сохраняется размер окна, минимум — один пиксель;
2. если окно больше доступной ширины/высоты, его начало ставится на границу;
3. близкий край притягивается к bounds при расстоянии до `14 DIP` в пересчёте на текущий DPI;
4. включённые ограничения зажимают координату в диапазоне монитора.

`EdgeConstraints` позволяет временно отключить clamp на общей границе соседних мониторов. Это важно: внутренний стык дисплеев должен быть проходимым во время drag, а внешний край — всегда защищённым.

## 5. Перетаскивание и последний защитный контур

Контроллер подключается к HWND через `HwndSource.AddHook` после `SourceInitialized` и обрабатывает сообщения Windows.

### Drag loop

- `WM_ENTERSIZEMOVE` включает режим native move loop.
- `WM_MOVING` получает предложенный `RECT` до его отображения системой.
- Текущий monitor определяется по курсору.
- Для соседних мониторов вычисляется `EdgeConstraints`: общая сторона отключает snap/clamp, внешние стороны остаются включёнными.
- Исправленный `RECT` записывается обратно в память сообщения.
- `WM_EXITSIZEMOVE` выполняет финальную нормализацию по последнему monitor и инициирует сохранение.

Это предотвращает ситуацию, когда окно сначала визуально уезжает за край, а исправление выполняется только после завершения drag.

### Programmatic moves

`WM_WINDOWPOSCHANGING` — финальный guard для изменений, пришедших не из drag loop:

- восстановление после запуска;
- reset position;
- смена layout;
- изменение масштаба;
- resize за углы;
- tray-команда «Показать виджет»;
- системные изменения мониторов и DPI.

Обрабатываются как операции только размера, так и операции только позиции. Если Windows выставила `SWP_NOMOVE`, но вычисленный безопасный X/Y отличается, контроллер снимает этот флаг и пропускает исправленную позицию.

Флаг `_applyingPlacement` защищает внутренний `SetWindowPos` от повторной обработки собственного изменения.

## 6. Resize за углы

Resize реализован как изменение общего масштаба с сохранением пропорций выбранного layout.

1. При нажатии в зоне `24 DIP` у угла запоминаются экранная точка, native RECT, DPI и текущий scale.
2. При движении мыши вычисляется delta в экранных координатах.
3. Delta проецируется на выбранный угол и переводится в scale относительно стартового размера.
4. Scale ограничивается диапазоном `0.6..2.0`.
5. `AnchorResize` удерживает левый/правый и верхний/нижний край в зависимости от угла.
6. Полученный RECT проходит через `ClampAndSnap` по физическим bounds монитора.
7. При потере capture или деактивации resize завершается и позиция сохраняется.

Таким образом, resize не может обойти защиту, действующую для drag и программного `SetWindowPos`.

## 7. Реакция на topology и DPI

Контроллер запускает 200-миллисекундный `DispatcherTimer` после следующих событий:

- `WM_DISPLAYCHANGE` — подключение, отключение или изменение дисплея;
- `WM_SETTINGCHANGE` — изменение системных параметров, включая taskbar/work-area;
- `WM_DPICHANGED` — изменение DPI;
- `WM_POWERBROADCAST` с `PBT_APMRESUMEAUTOMATIC` — возврат после сна.

После debounce выполняется `NormalizeCurrentWindow(false)` и сохраняется актуальное placement. Во время restore при смене monitor или DPI используется двухфазный сценарий:

1. окно временно помещается в безопасную точку текущего монитора;
2. после завершения WPF/DPI transition placement рассчитывается заново по сохранённому monitor identity, anchors и относительным координатам.

## 8. Сохранение и восстановление

Профиль хранится в:

```text
%LOCALAPPDATA%\LLMLimitsWidget\widget-settings.json
```

Сохраняются:

- `Orientation`, `Scale`, `SurfaceOpacity`, `CornerRadius`;
- имя монитора `MonitorDeviceName`;
- стабильные идентификаторы `MonitorDeviceId` и `MonitorDeviceKey`;
- `RelativeX` / `RelativeY` в диапазоне `0..1`;
- `PlacementAnchor` для прилипания к краям;
- сохранённый DPI;
- последние bounds монитора для fallback-поиска.

При сохранении `Capture` сначала определяет anchors, если окно находится в пределах трети snap-distance от края. Если anchor отсутствует, координата нормализуется относительно пространства `monitorBounds - windowSize`, а не относительно taskbar/work-area.

При восстановлении monitor выбирается в порядке приоритета:

1. `MonitorDeviceKey`;
2. `MonitorDeviceId`;
3. `MonitorDeviceName`;
4. ближайший по центру monitor из доступных;
5. monitor под курсором, если профиль отсутствует.

Профиль нормализуется при загрузке: scale, opacity, corner radius и relative coordinates ограничиваются допустимыми диапазонами. Ошибки JSON, блокировка файла, отсутствие каталога или отказ доступа приводят к default settings и не блокируют запуск виджета.

Запись выполняется через временный файл в том же каталоге и последующий replace, поэтому незавершённая запись не должна оставить основной JSON частично перезаписанным.

## 9. Tray и видимость окна

Tray icon создаётся в `App` через `NotifyIcon`. Само overlay-окно имеет `ShowInTaskbar="False"`, поэтому отдельная кнопка приложения в taskbar не создаётся.

Команда «Показать виджет»:

1. показывает окно;
2. возвращает `WindowState.Normal`;
3. вызывает `EnsureVisible`;
4. нормализует текущий RECT по физическому monitor bounds;
5. активирует окно.

Команда «Сбросить позицию» ставит виджет у правого нижнего физического края текущего monitor. Этот край может совпадать с областью taskbar.

## 10. Тестирование

Чистая геометрия проверяется проектом `FloatingOverlay.GeometryTests`:

```powershell
dotnet run --project .\spikes\FloatingOverlay.GeometryTests\FloatingOverlay.GeometryTests.csproj --no-restore
```

Проверяются:

- отсутствие изменений внутри bounds;
- clamp со всех четырёх сторон;
- snap к краям;
- overlap зоны taskbar внутри `rcMonitor`;
- отрицательные координаты монитора;
- смещённые bounds;
- окно больше монитора;
- переполнение по двум осям;
- anchors при restore после смены размера/DPI;
- проход через общую границу соседнего монитора;
- защита внешней границы.

Сборка:

```powershell
dotnet build .\spikes\FloatingOverlay\FloatingOverlay.csproj
```

На момент фиксации реализации: сборка проходит без ошибок и предупреждений, geometry suite — `19 cases passed`. Дополнительно выполнена ручная Win32-проверка реального HWND: окно было выставлено поверх taskbar и осталось внутри `rcMonitor`.

## 11. Ограничения текущего spike

- Данные лимитов пока sample/mock и не подключены к provider adapters.
- Geometry tests не заменяют полноценный UI automation test на нескольких физических мониторах.
- Сохранение настроек best-effort: при недоступном `%LOCALAPPDATA%` приложение продолжает работать, но профиль не обновляется.
- Перекрытие taskbar является осознанным UX-решением; виджет не является встроенным дочерним элементом штатного taskbar.
